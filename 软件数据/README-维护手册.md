# 软件数据维护手册

> 本文件夹为网站的「软件数据」区：**每个软件对应一个文件**，互不影响。
> 分类 → `categories.json`；软件 → `apps/` 文件夹；页面代码无需修改。

---

## 一、添加新软件（3 步）

1. 打开 `apps/` 文件夹，**复制 `_模板.json`**，粘贴后重命名为 `软件英文id.json`
   （例如添加「记事本」则命名为 `notepad.json`；名称可自定，仅限英文小写与短横线，不使用中文和符号）
2. 打开该文件，将模板中各字段的值改为新软件的信息
   （每个字段旁均注明应填写的内容）
3. 保存。开发预览（`npm run dev`）下浏览器会**自动刷新**并显示结果；
   正式发布前执行一次 `npm run build`（如需单文件版则执行 `npm run build:single`）

> 新软件默认显示在列表末尾。如需插入中间位置，修改 `sort` 数值即可
> （数值越小越靠前，例如需排在第 3 位则填 2；0 表示最前）。

---

## 二、修改与删除软件

- **修改信息**：直接打开 `apps/<id>.json` 编辑，保存后即生效。
- **删除软件**：删除对应的 `.json` 文件即可。

> **别人提交上来的草稿（`[待审核] …` 工单）怎么处理？** 在 Issue 上打标签，机器人会自动办：
>
> - `approved` —— 通过，合并成 `apps/<id>.json`。**若站内已有同 id 文件，它会直接拒绝并说明**
>   （这一步是故意加的，防手滑覆盖已发布的数据）。
> - `覆盖已存在` —— 确实要用这次提交**整份替换**站内那份时才打。图标 / 版本号 / 下载直链全部以
>   提交内容为准；机器人会把「改前 → 改后」的字段差异和**旧版完整内容**贴进 Issue，旧版也能从
>   提交历史找回（`git show <父提交>:软件数据/apps/<id>.json`）。
>   ⚠️ 草稿信息比站内**少**时（常见：只剩一条「官方安装网站」链接、`icon` / `version` 为空）别用它 —— 那样是倒着走，直接 `rejected` 更合适。
> - `rejected` —— 不要这份提交，删掉草稿并关闭工单。

## 三、字段说明（与原版 HTML 中的注释一一对应）

| 字段 | 含义 | 注意事项 |
|---|---|---|
| `id` | 唯一英文标识 | **不可重复**；网址为 `#/download/<id>`；仅允许英文小写、数字与短横线，**不得包含 `?` `&` `=` 等符号** |
| `name` | 软件名称 | 无限制 |
| `icon` | 图标图片链接 | 建议使用正方形（256×256）；留空则显示空白占位 |
| `category` | 所属分类 | 必须是 `categories.json` 中的 key：`system`(系统工具) / `schedule`(教学软件) / `teaching`(教学辅助) / `other`(其他工具) |
| `tagline` | 一句话简介 | 显示在首页卡片上 |
| `description` | 详细介绍 | 显示在详情页 |
| `version` | 版本号 |  |
| `size` | 软件体积 | 同上 |
| `system` | 系统限制 | 如 `Windows 10/11（x86 / x64 / ARM64）、macOS、Linux` |
| `website` | 官方网站 |  |
| `github` | GitHub 仓库 |  |
| `notice` | 更新提示（可选） | 适用于更新频繁、直链容易失效的软件，填写一句话说明。显示在详情页「下载」上方的蓝色提示条。不需要时整行删除 |
| `store` | 应用商店链接（可选） | 填写商店网页地址（如 `https://apps.microsoft.com/detail/xxxx`）。详情页会增加「使用 Microsoft Store 下载」入口。不需要时整行删除 |
| `downloads` | 下载项数组 | 见下方模板；每个平台 / 架构为一项 |
| `sort` | 显示顺序 | 数值小的靠前；一般无需修改 |
| `维护备注` | 维护者备注 | 网页不显示，可自由填写 |

> **必填项**（提交页 `#/submit` 会拦下不填的）：`id`、`name`、`tagline`、`description`、`system`、`联系方式`、`downloads[].url`。
> 其中 `system` 技术上可以留空（详情页会显示「待补充」），但空着别人没法判断自己的电脑能不能装，所以也列为必填；
> 从 GitHub 一键读取时会自动归纳填上（如 `Windows 10/11（x86 / x64 / ARM64）`），手填也就一行字。
>
> ✅ **关于「联系方式」的坑（2026-09-19 已修）**：它写成草稿里的 `_联系方式`，属于**审核用字段** ——
> 审核通过时 `review-submission.yml` 会剥掉所有 `_` 开头的键，所以它**不会被发布到网站上**。
> 提交接口（`#/submit`）原先只按字段白名单重建草稿，把这个键整个丢了，审核工单于是显示成「没有联系方式」。
> 当天已改提交服务（Cloudflare Worker `classhub`）：**凡入参里 `_` 开头的键都原样带进草稿**，
> 顺手也修了 `downloads[].hash`（校验值）被丢的同类问题。源码备份在 `submit-worker/`。
> ⚠️ 那次修复**之前**提交的草稿是真没有这个键，遇到就请提交者在审核工单下面回一句。

`downloads` 中每一项的格式如下（注意使用**英文逗号**分隔，最后一项后不加逗号）：

```json
{
  "platform": "Windows x64 安装版",
  "note": "官方安装包，GitHub 链接有时不稳定",
  "size": "373 KB",
  "hash": "3F7A9C1D…（完整校验值，可整行删掉）",
  "url": "https://github.com/xxx/xxx/releases/download/xxx.exe"
}
```

- `url` 必须是**文件直链**（.exe / .zip / .msi 等），点击后**立即开始下载**，不要填写官网下载页地址。
  没有直链时可将该项删除或暂不填写；也可将官网下载页作为一项写入，把 `size` 填为「网页」并在 `note` 中说明。
- `hash` 是**校验值**（可选）：只填**十六进制那一串**，算法不用写 —— 详情页会按长度自动识别
  （`32`=MD5、`40`=SHA-1、`56`=SHA-224、`64`=SHA-256、`96`=SHA-384、`128`=SHA-512）。
  页面里只显示首尾各几位（如 `SHA-512 3F7A9C1D…B2E8F4`），鼠标悬停看完整值，**点一下就复制**。
  > ⚠️ 不要把校验值整串写进 `note`：128 位没有可断行的地方，会把文字**画出卡片**。
  > 已有数据里如果这么写过，把哈希挪到 `hash` 字段、`note` 只留人话即可。
  > 提交页 `#/submit` 的下载项里也有「校验值」输入框（选填）：带 `MD5:` 前缀、按字节用冒号或空格分隔的写法都能直接粘，
  > 页面会先归一化成纯十六进制再提交；字符不是十六进制、或位数对不上任何一种算法（32/40/56/64/96/128）时，点提交会被当场拦下。
- 多个下载项在数组中以 `{ ... },` 形式用逗号分隔。

### `notice` 与 `store` 的适用场景

- **更新频繁的软件**（如 PowerToys、ToDesk、驱动总裁等）：写死直链后很快会失效。
  两种处理方式：
  1. 只填写**官网「始终最新」的链接**（多数官网提供此类固定地址），或在 `downloads` 中放入官网下载页；
  2. 填写 `notice`，提示用户前往官网或应用商店获取最新版。
- **应用商店提供官方版本的软件**（PowerToys、VLC、GeoGebra、UU远程、图吧工具箱等）：
  填写 `store` 后，详情页会出现「使用 Microsoft Store 下载」按钮 —— 商店版本**自动更新**，
  无需跟进版本，可将版本维护交由商店完成。
  > 无需刻意填写 `store`：只要 `downloads` 中有一项的 `url` 指向 `apps.microsoft.com` 商店页
  > （早期软件即为此写法），详情页会**自动识别**并渲染为同一张商店卡片，不再重复显示为普通下载项。
  > 两种写法均可，按习惯选择。

## 四、分类修改（一般无需改动）

`categories.json` 中包含 4 个分类（key / 名称 / 图标）。修改名称直接编辑 `name` 字段。
图标 `icon` 为字体符号代码（形如 `\uE90F` 的转义形式），修改需要对照 Fluent 图标表，**不建议随意改动**。

## 五、JSON 语法说明

- 每行格式为 `"字段名": 值` —— 冒号、引号、逗号均需使用**英文符号**。
- 字符串（文字、网址）需用**英文双引号**包裹。
- 最后一行的值后面**不加**逗号。
- 无法确定时，复制 `_模板.json` 后修改，不要从空白开始手写。

**格式错误的影响**：网站具备容错机制 —— 单个文件格式错误只会跳过该文件，其余内容正常显示；
页面**顶部会出现红色提示条**，标明：「有 N 个数据文件未读取」+ 每个错误文件的名称 + 大致错误行号 + 原因
（鼠标悬停在提示条条目上可查看浏览器原始报错）。
修改后保存并刷新即可看到提示条，改正后提示条自动消失 —— 不会出现整站无法打开的情况。

## 六、软件版本自动核对

网站仓库**每周五上午**会自动核对每个软件的版本号、下载直链与体积。

核对来源**只有 GitHub Releases 一条** —— 认软件的 `github` 字段，本站收录的开源软件都走这条。

> **2026-09-21 起，原来那条「非 GitHub 官方来源」的腿已停用。**
> 当时它负责抓取希沃产品清单、VideoLAN 目录、360 页面、DiskGenius 更新日志、GeoGebra 重定向
> 等厂商页面，覆盖 10 个**没有 GitHub 仓库**的软件（希沃白板 / 希沃品课 / 希沃课堂助手 /
> 视频展台 / 班级优化大师 / 360急救箱 / 360极速浏览器 / VLC / GeoGebra / DiskGenius）。
> 停用的理由：厂商一改版就得跟着改解析规则，维护成本高、收益不抵。
> 这 10 个软件现在落在「跟不了 → 只有网页入口」那一档，理由里写明了停跟的原因。
> 解析规则**仍保留**在 `scripts/update-channels.mjs`（开关 `CHANNELS_ENABLED = false`），
> 想恢复第二条腿：把开关改成 `true`，并删掉 `BUCKETS` 里这 10 条登记（不删也无妨）。

- **可确定的更新由脚本自动写入**（更新版本号、更换直链、修正体积），无需人工介入；
- **无法确定的条目**会汇总到「软件信息体检」Issue 中，
  每条均注明「需跟进」与「不跟进」两种处理方式。

在该 Issue 中，每条记录包含标题、一行「未自动修改的原因」、**三个复选框**，以及折叠的「跟进修改步骤」。

| 处理意图 | 操作方式 |
|---|---|
| 已在其他地方修改完成，需要重新检测 | 修改并**提交**后，勾选该条的「**已改好 → 重新检测**」 —— 系统会立即重新执行检查，修改正确则该项消失 |
| 这次先不管（**有变化再提醒**） | 勾选该条的「**本次跳过**」复选框 —— 只压住当前这一版问题 |
| 该软件不再维护（今后不再提醒） | 勾选该条的「**不用跟进**」复选框（永久忽略） |
| 误操作 / 需恢复提醒 | 在 Issue 文末「已忽略 / 本次跳过」区域勾选对应那条的「恢复提醒」 |
| 需要写明忽略理由（也支持批量处理） | 回复 `/ignore 软件id`、`/ignore 软件id all 理由`、`/unignore 软件id` |

> 修改后**必须先提交**（网页端为 Commit changes）再点击「重新检测」，否则系统读取的仍是旧数据。
> 三个复选框均为**一次性操作，不是待办项**：勾选后该项即从清单中移除，无需保留勾选状态。
> 「**本次跳过**」与「**不用跟进**」的区别：前者只跳过**当前这一版问题**（上游一发新版、直链一换
> 就会自动回来提醒），后者是永久静音。拿不准时用「本次跳过」—— 它不会让你以后收不到真问题的提醒。
> 跳过记录保存在 `软件数据/update-ignore.json` 的 `_skip_once` 字段里（不是忽略条目）。
> `软件id` 即 `apps/` 中文件名去掉 `.json` 后的部分，例如 `7-zip`、`classisland-17`（使用复选框时无需记忆）。
> 记录保存在 `软件数据/update-ignore.json`，也可手动修改（删除对应行即恢复提醒）。

**需要人工确认的情况**（均为脚本无法代为决定的情形）：

- **跨大版本更新**（例如 1.7 → 2.0）—— 站内可能有意保留旧版供旧电脑使用；
- 下载项的 `note` 中包含 **SHA512 / SHA256 校验值** —— 文件更换后校验值即失效，需重新计算；
- 上游**修改了文件名**，`downloads` 里找不到对应的下载文件；
- `github` 字段填写的仓库无法打开，或填写的并非仓库地址；
- **非 GitHub 直链仍指向旧版本**（官网 / 镜像链接中仍为旧版本号）—— 脚本不会代为修改此类链接；
- 下载直链已失效（访问返回 404）。

> 全部处理完成后，该 Issue 会**自动关闭**，无需手动操作。

### Issue 里的「跟不了」是什么

Issue 的正文**刻意写得很短**：顶部一行数字，下面**只列需要你处理的条目** ——
已自动更新、跟不了、已忽略、本次跳过、账目都收在折叠区里。

顶部那行是**唯一**一套数字，而且是**互斥、可相加**的四类（文末「本次账目」会逐条列出 id，
四类相加必须等于软件总数 —— 不相等时脚本日志里会报「账目不平」）：

| 归属 | 含义 |
|---|---|
| **要你处理** | 产生了待审条目的软件。即使本次也自动修好了一部分，也只算一次 |
| **本次自动修好** | 脚本写回成功、且没留下待审条目的 |
| **跟踪中、不用管** | 其余在自动跟踪的（已最新 / 比上游新 / 上游暂无发行版） |
| **本来就不跟** | 没有 GitHub 仓库、也不做页面抓取的，见下方那张表 |

> ⚠️ 别在这里再放第二套口径不同的统计。以前顶部写「要你裁决 / 已自动更新 / 自动跟踪 / 跟不了」，
> 文末又写「已是最新 / 站内落后 / 需人工 / 查询失败」—— 前者是**条目数、且已过滤忽略清单**，
> 后者是**软件数**；前者是写回**之后**的事实，后者是检查**那一刻**的快照。两套账摆在一起，
> 就会出现「已自动更新 7 个」和「站内落后 6 个」互相打脸的数字（本次已由 `reconcile()` 统一）。
> 「体检状态细分」那一行可以留，但必须注明它是「同一批软件的另一种看法，不另外计数」。

「跟不了」那张表把**没法自动跟踪**的软件按原因分档列清楚，**它们不会变成待办条目**
（点不动的方框只是噪音）：

| 档位 | 含义 | 要人管吗 |
|---|---|---|
| **只有网页入口** | 官网是 JS 渲染的 SPA 抓不到版本；**或**上游没有 GitHub 仓库、已停止页面抓取（2026-09-21 起） | **要**，偶尔看一眼 |
| **微软商店分发** | 商店自己会推送更新，站内只做跳转 | 不用 |
| **官方固定「最新版」直链** | URL 永不过期（如 `.../Version/Latest/`），装完软件自己也会更新 | 不用 |
| **有意归档 / 已停更** | 故意收录的旧版（id 里带版本号就是信号） | 只需盯「官方是否撤链」 |
| **第三方网盘** | 蓝奏云 / 百度网盘分发，链接没法自动验证 | 偶尔看一眼发布页 |

**新增软件时**：如果它没有 GitHub 仓库，顺手去 `scripts/update-channels.mjs` 的 `BUCKETS` 里
补一条（写明属于哪一档、为什么），这份覆盖表才一直是真的 —— 否则它会落在「只有网页入口」
的兜底档里，理由写成「还没登记来源」，看起来像没人管。
